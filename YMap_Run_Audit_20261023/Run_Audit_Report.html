2. The measurement scenario is specific

The manifests record PostgreSQL 14.24, a Windows 11 / Python 3.13.5 client and psycopg 3.3.6. The generated fixture uses 100 logical objects per concrete class, seed 42, point lookups, ordered limited scans and association joins. Query limits are 100; caches are not forcibly evicted. This is a small reference workload, rather than the original manuscript protocol. [D]

Insertion timing includes client batching, network, indexes, constraints and commit, while excluding DDL and fixture generation. Query timing includes result fetching after loading and ANALYZE. Storage is total base-table/index/TOAST bytes divided by 1,000,000. These boundaries must accompany any reported result.

Repeat variability is material: median within-schema coefficient of variation is 25.8% for insertion and 23.2% for queries. This describes the five timed repeats; it does not establish the cause or justify deleting observations. Server hardware, storage and concurrent load are not fully characterized. [A, D]

Hypervolume uses the recorded normalized metric coordinates and reference point; it is not a percentage and need not lie below 1. The mean measured-front hypervolume is 1.1180.

The ensemble has negative query R² in all 11 systems: its absolute query predictions perform worse than each test system's constant-mean reference under this metric. Ranking differs from calibration: macro within-system Spearman correlation is 0.8722 for storage, but only 0.3549 for insertion and −0.0436 for query latency. Storage ranking therefore contains useful signal even though absolute predictions transfer poorly.

All 30 paired comparisons of recommendation-quality metrics have Holm-adjusted p = 1.0; the smallest unadjusted p is 0.3008. These are not significance tests of predictive error. No superiority is established. With only 11 independent systems, nonsignificance also does not establish equivalence. Risk adjustment changes selections only for blog_platform, where F1 falls by 0.1333 and hypervolume by 0.0621; it provides no observed overall benefit here. [A]

Three MLP folds reached 500 iterations without convergence. Linear and MLP models produced three and four negative insertion predictions, respectively. These outputs remain unchanged; a positive-target transform or constrained predictor would be a new modeling choice requiring validation.

4. The current representation loses distinctions

728 physical candidates collapse to only 226 distinct structural feature vectors. There are 112 collision groups containing 614 candidates, including four groups spanning different source systems. ERP alone has 384 candidates but only 44 feature vectors. [B]

Different SQL structures can therefore receive identical input vectors and necessarily identical deterministic predictions. Their recorded costs differ. This is a plausible limitation of the representation, rather than proof that it alone causes the observed errors: measurement variability and source-system shift also remain. No exact duplicate physical declarations were detected by this audit.

A concrete hospital_information_system pair has identical 16-feature vectors, yet its mappings require 1,700 versus 1,900 physical insertion rows and 600 versus 800 deferred-trigger insertion events. The count vector omits these distinctions. Those structural differences support diagnosis; they do not isolate a causal timing effect. [B]

5. Preference regret needs a precise label

The saved metric is mathematically consistent, but evaluates the best measured utility inside the returned set. It assumes an oracle can identify that member after observing costs. A deployment decision instead selects one schema using predictions alone. The audit reconstructed that choice from recorded preference scores without using test outcomes to choose it. [C]

6. The next step reuses the existing measurements

  1. Freeze this run. Preserve candidates, raw logs, predictions, configurations, hashes and current results as the baseline. Do not blindly repeat all 728 database profiles.
  2. Check the training machine. Confirm RAM, available GPU/VRAM, PyTorch and device support before selecting neural settings.
  3. Test the existing graph + symbolic ablation. It can use the current measured candidates and richer graph structure without pretrained text checkpoints. Keep source-system separation, training-only transformations and the same measurement scenario.
  4. Evaluate full multi-view modeling only if needed. Use actual authorized local checkpoints with their tokenizers and recorded identities. GraphCodeBERT's text view here uses its standard text interface; the separate schema graph encoder supplies relational structure. No improvement is promised.

Protect the evaluation boundary. Any feature, hyperparameter or risk-weight revision motivated by these outer-test results is exploratory. Confirmatory improvement claims require nested or independent reassessment. Additional database measurements should follow a specific protocol gap or scientific question, not an attempt to force stronger scores.
